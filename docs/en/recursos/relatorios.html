Reports and processing

Persistent reports let administrators inspect many courses and return to progress later without relying on an open browser tab.

Snapshot creation

Generating a report creates a parent record and one row for each course, including its ID, display name, initial status and counters. HTML and multilang markup are normalised into readable names before storing snapshots.

Cron and AJAX

Moodle ad-hoc tasks inventory courses one by one. Meanwhile, the browser polls the report state over AJAX to display progress, completed or failed course counts and captured references. Browser requests do not execute the backup work.

Sequential execution

A report-level lock avoids running the same report concurrently. After one course is processed, the next task is queued. A failed course is recorded and does not automatically block remaining courses.

Completion and navigation

When processing ends, the progress page automatically opens the comparison. Later visits to a completed or partially completed report go directly to its comparison page.

Retries and history

Administrators can request retries for failed courses. The landing page lists recent reports and allows authorised deletion. A configurable maximum number of reports controls retention.

Task states

Course jobs use pending, running, completed and failed. Main report states include queued, running, completed and partial, which indicates one or more course failures.

100% progress means that every course finished processing or reached a failure state. Review failed courses before treating the inventory as complete.
