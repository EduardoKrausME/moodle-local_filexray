How the inventory works

File X-Ray uses native backup plans to collect file references without copying them into a new archive.

One course at a time

Each report stores one row per course. The task runner acquires a report-scoped lock, selects the next pending course and executes that course's native backup plan. This is not a single long-running AJAX request.

Native annotations

The native Moodle course backup workflow collects file references from supporting components. Once IDs have been consolidated, File X-Ray saves selected IDs from backup_ids_temp and mdl_files, including content hashes, components, file areas, contexts, names and byte sizes.

Where processing stops

The plugin stops before the fileslist step, which would copy physical file contents and prepare the final archive file list. It never executes MBZ packaging or destination storage. Earlier steps may create temporary XML data, which the plugin cleans up.

What gets captured

The inventory covers references resolved by Moodle's course backup mechanisms and compatible plugins. It does not claim to cover user-only files, global contexts or components that do not participate correctly in course backup.

Failures and upgrades

A failed course retains its error status in the report. The order of native backup steps matters and should be checked when Moodle updates alter backup APIs.

A record not selected by backup is not necessarily unused. The inventory captures the backup-selected set, not every possible dependency in Moodle.
